# GitHub 저장소 외부 API 현황 분석 도구 — 제품 요구사항

웹 애플리케이션 개발·유지보수자가 공개 저장소의 외부 API와 호출 위치를 파악하는 도구. 제품명은 임시 설명명이다.
출처: scope.md > The Unique Kernel, Who It's For, The Core Loop.

## The Core Journey
1. GitHub 계정으로 로그인한다.
2. 이전에 등록한 저장소 목록을 확인한다. 처음이면 목록은 비어 있고 새 저장소 추가가 가능하다.
3. 새 저장소 추가에서 공개 GitHub 저장소 주소를 입력한다.
4. 기본값으로 즉시 분석한다. 계정 설정에서 자동 분석을 끈 경우 등록만 하고 수동 실행한다.
5. 분석 중에는 “분석 중”을 표시한다.
6. 완료하면 왼쪽 API 목록에서 항목을 선택하고 오른쪽에서 상세 정보를 확인한다.
7. 같은 계정으로 다른 기기에 접속해 목록·설정·저장된 결과를 다시 본다. 필요할 때 재분석한다.
출처: scope.md > The Core Loop, What "Working" Looks Like. 계정과 동기화는 범위 승인 이후 사용자가 명시적으로 추가한 요구사항이다.

## Screens and Layout
- 로그인 진입: GitHub 계정으로 접속한다.
- 저장소 목록: 등록한 저장소와 새 저장소 추가 버튼. 주소 입력을 제공하고 저장소의 분석 결과로 이동할 수 있다. 추가 입력의 모달/별도 화면 여부는 구현 배치 선택으로 남긴다.
- 분석 결과: 왼쪽에 API 목록, 오른쪽에 선택한 API 상세. 상세에는 API 식별 정보, 호출 파일과 관련 기능 및 근거, 등록된 점검 대상의 최근 점검 결과·시점 또는 미설정 이유를 표시한다. 분석 시점과 최근 시도 상태를 구별한다.
- 계정 설정: 등록 직후 자동 분석의 켜기/끄기. 기본값은 켜짐이다.

## Features and Behavior

### GitHub 로그인과 계정별 동기화
GitHub 계정에 저장소 목록, 자동 분석 설정, 분석 결과를 연결한다. 같은 계정은 다른 기기에서 동일 정보를 볼 수 있고 다른 계정의 개인 목록과 결과는 접근할 수 없다. 로그인 실패 시 이유와 다시 시도할 동작을 제공한다.

### 저장소 등록과 분석 실행
공개 GitHub 저장소 하나의 주소를 입력해 등록한다. 기본 자동 분석 또는 설정에 따른 수동 분석, 기존 저장소 재분석을 지원한다. 사용할 수 없는 주소·비공개/접근 불가 저장소는 사유와 함께 실패로 안내한다.
출처: scope.md > The POC Boundary, Explicitly Cut.

### API 목록과 상세
탐지 가능한 외부 API를 모아 보여준다. 선택한 API의 호출 파일, 관련 기능, 코드 근거를 오른쪽에서 확인한다. 추론이 어려운 기능은 확인 불가 또는 불확실하다고 표시한다. 코드 분석 결과와 실제 점검 결과를 구분한다. 점검 기준 통과를 서비스 전체 정상으로 해석하지 않는다.
출처: scope.md > The Unique Kernel, The POC Boundary.

### 분석 상태와 실패
분석 중에는 “분석 중”만 표시한다. 실패는 “분석 실패”와 사유를 표시한다. API 미검출도 실패로 안내하되 “지원하는 탐지 방식으로 외부 API를 찾지 못했습니다”처럼 표현하고, API가 없다고 단정하지 않는다. 실제 사유를 알 수 없을 때는 추측해 단정하지 않는다.

### 결과 저장과 교체
저장소마다 마지막 성공 결과 하나 및 그 분석 시점, 최근 분석 시도의 상태와 시점·실패 사유를 보관한다. 성공 시 기존 성공 결과를 새 결과로 교체한다. 실패·미검출 시 이전 성공 결과는 유지하고 최근 시도가 실패했음을 별도로 표시한다. 이전 성공 결과가 없으면 실패 안내만 표시한다. 결과 이력 여러 개는 보관하지 않는다.

## Acceptance Criteria
- 같은 GitHub 계정으로 다른 기기에 접속하면 등록한 저장소, 자동 분석 설정과 마지막 성공 결과가 보인다.
- 다른 계정으로 접속하면 해당 사용자의 저장소 목록과 저장 결과가 보이지 않는다.
- 자동 분석 기본값에서 공개 저장소 등록 직후 “분석 중”이 보인다. 끈 경우 등록만 되며 수동 실행이 가능하다.
- 알려진 외부 API 호출이 있는 지원 예제 저장소를 분석하면 API와 실제 호출 파일·관련 기능 근거가 대응한다.
- 왼쪽 API를 선택하면 오른쪽 상세가 해당 API로 바뀐다.
- 점검 미설정 대상은 확인 불가와 이유를 표시한다. 설정된 대상은 최근 점검 시점과 기준 통과 여부를 표시한다.
- 실패와 미검출에서 실패 안내와 사유가 보인다.
- 성공 후 재분석 실패 시 이전 성공 결과·분석 시점과 최근 실패 사유가 함께 보인다. 다음 성공 시 최신 성공 결과로 교체된다.
출처: scope.md > What "Working" Looks Like 및 후속 사용자 결정.

## States and Boundaries
- 최초 사용: 등록 목록이 비어 있으며 새 저장소 추가가 가능하다.
- 등록만 완료: 자동 분석을 끈 경우 아직 분석하지 않았음을 구분하고 수동 실행이 가능하다.
- 분석 중: 분석 중 문구를 표시한다. 진행률·단계 상세는 요구하지 않는다.
- 분석 성공: API 목록과 선택 상세, 성공 분석 시점을 표시한다.
- 분석 실패/미검출: 실패 사유를 표시한다. 이전 성공 결과가 있으면 오래된 결과임을 구분해 유지한다.
- 로그인/저장 실패: 실패 이유를 안내하고 저장되지 않은 정보를 저장된 것으로 표시하지 않는다.
- 공개 저장소만 분석한다. 로컬 실행 환경은 연결하지 않는다. 사용자가 점검용 인증 정보를 별도로 등록할 수 있다. 모든 외부 API 탐지를 보장하지 않는다.

## Product Decisions
- 계정별 동기화: 여러 개발 환경에서 저장소를 반복 등록하는 번거로움을 줄이기 위해 추가했다.
- 등록 직후 자동 분석: 기본 켜짐이며 계정 설정에서 변경한다.
- 왼쪽 API 목록과 오른쪽 선택 상세 배치.
- 분석 결과도 저장하되 최신 성공 결과 하나만 유지한다.
- 재분석 실패는 마지막 성공 결과를 지우지 않고 별도 상태로 표시한다.
- 분석 중은 간단한 문구, 실패/미검출은 사유를 포함한다.
- 한국어, Docker Desktop 참고, 지정한 네 가지 색상 사용.
- 무료 DB 서비스(예: Supabase)와 웹 배포 서비스(예: Vercel) 사용 희망. 서비스 선택·이용 조건은 기술 계획에서 검증한다.

## What We're Building
GitHub 로그인, 계정별 저장소 목록·설정·결과 동기화, 공개 저장소 등록, 자동/수동/재분석, API 목록과 호출 위치·관련 기능 상세, 분석 상태와 실패 처리, 마지막 성공 결과 보존, 하루 한 번 API 점검·인증 정보 등록·사용자 지정 판정 조건.

## Deferred From the POC
사용법 안내 추가는 사용자 요청에 따라 나중에 진행한다. 보안·권한 분석과 장애 대응 분석·장애 테스트는 승인한 후속 확장으로 유지한다.
출처: scope.md > Later.

## Non-Goals
비공개 저장소 분석, 로컬 실행 환경 연결, 모든 API의 완전한 정상 동작 보장, 자동 장애 주입, 모든 언어·간접 호출의 완전 탐지, 여러 분석 결과 이력 저장은 첫 시제품에서 제외한다.

## Open Questions
- 기술 계획에서 확정: 지원 언어·호출 패턴·저장소 규모와 탐지 한계, 관련 기능의 코드 근거 표시 기준. 지원 범위는 구현 전에 명시하고 예제 저장소로 확인한다.
- 기술 계획에서 검증: 무료 DB/배포 이용 조건 및 GitHub 로그인 설정, 계정별 접근 제어, 분석 실행 제한. 계정 기능 추가로 작업량이 늘었으므로 기존 2~4시간 목표 달성 여부를 재평가한다.
- 제품 이름은 현재 임시 설명명이며 출시 전 변경 가능하다.

## Scheduled API Checks
사용자가 발견된 API에 점검 주소와 필요한 읽기 전용 API 키·고정 토큰을 별도로 등록한다. 자동 점검은 기본 켜짐이며, 등록된 점검 대상 전체를 하루 한 번 점검한다. 계정 설정에서 비활성화할 수 있고 이 설정은 같은 계정의 다른 기기에도 유지된다. 이는 저장소 코드 재분석과 별도 기능이다. 정확히 24시간 간격·정각 실행을 보장하지 않으며 실제 예약 방식과 시간 표시를 기술 계획에서 확정한다.

### Check Criteria
- 기본값: HTTP 2xx 응답이면 설정한 점검 기준 통과.
- 사용자는 예상 HTTP 상태 코드와 JSON 응답의 특정 필드 경로·예상 값을 추가 지정할 수 있다. 지정한 조건은 모두 만족해야 통과한다.
- 상태 코드 불일치, 지정 필드 누락·값 불일치, JSON 조건을 설정했으나 JSON으로 해석할 수 없는 응답은 기준 미충족과 구체적 이유를 표시한다.
- 인증·권한 거절, 요청 한도 초과, 서버 오류, 시간 초과·연결 실패를 관찰된 근거로 구분한다. 가능한 원인을 확정된 근본 원인처럼 단정하지 않는다.
- 사용자에게 “설정한 점검 기준 통과 / 미충족 / 실행 실패 / 미설정”을 구별해 보여준다. 최근 점검 시점과 응답 코드·응답 시간을 함께 저장한다. 실패를 과거 통과로 덮어 표시하지 않는다.
- JSON 응답 본문 전체는 저장 요구사항에 포함하지 않는다. 점검 결과 저장과 코드 분석 성공 결과 보존은 구별한다.

### Credential Boundaries
읽기 전용으로 발급한 점검용 API 키·고정 토큰만 지원하며 OAuth 자동 갱신은 제외한다. 모든 공급자의 읽기 전용 권한을 자동 판별할 수 있다고 주장하지 않는다. 사용자는 인증 정보를 교체·삭제할 수 있어야 한다. 저장된 비밀값을 다시 화면에 노출하지 않으며 로그와 결과에 남기지 않는다. 사용자별 접근 제어와 서버 측 암호화, 등록된 전송 대상 제한을 기술 계획에 포함한다. 읽기 전용 키라도 API 요청의 부작용을 보장할 수 없으므로 점검 전용 조회 주소를 사용한다.

### Check Acceptance Criteria
- 자동 점검은 기본 켜짐이다. 등록 대상이 하루 한 번 예약 점검 대상에 포함되고 계정 설정에서 비활성화하면 새 자동 점검이 시작되지 않는다. 같은 계정의 다른 기기에서도 변경한 설정이 유지된다.
- 200 응답은 기본 조건에서 통과한다. 예상 코드 200과 JSON status=ok를 지정했을 때 status=error이면 미충족이다.
- 필드 누락·비JSON·타임아웃·401·429 등에서 관찰 결과와 이유가 구별된다.
- 다른 사용자의 인증 정보를 조회·사용할 수 없으며 저장한 비밀값이 화면·로그·점검 결과에 나타나지 않는다.
- 최신 점검 결과와 시점이 같은 계정의 다른 기기에서도 보이고, 코드 분석 결과의 시점과 구별된다.

### Remaining Check Decisions
기술 계획에서 지원 인증 헤더 방식, JSON 필드 경로 문법·값 타입, 조회 요청 방식, 타임아웃과 호출 제한, 외부 주소 검증·리디렉션 정책, 암호화 키 관리, 예약 실행 방식을 확정한다. 자동 점검의 최초 기본값은 사용자 결정에 따라 켜짐이다.

## Scope Amendment
범위 승인 후 사용자가 GitHub 계정 동기화, 저장 결과, 하루 한 번 실제 API 점검과 인증 정보 등록 및 판정 조건을 추가 요청했다. 이 PRD 초안은 확장한 요구사항의 검토본이며 기존 scope의 실제 점검 제외 결정을 대체하는 변경안이다. 보안·권한의 자동 분석과 장애 주입 테스트는 계속 제외한다. 계정·예약·비밀값 관리까지 포함하면 원래 2~4시간 학습 목표보다 커질 수 있어 기술 계획에서 작업을 분리한다.
